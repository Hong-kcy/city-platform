第一大阶段：Demo MVP——跑通完整产品闭环
阶段目标

使用尽可能低的技术复杂度，完成一个可以实际运行、可以展示、可以验证产品逻辑和商业闭环的 Demo。

Demo 阶段重点验证：

真实街区空间 → 商户与活动 → 用户发现 → 主题路线 → 基础推荐 → 到店任务/优惠 → 消费闭环

本阶段暂不追求完整的城市级地图能力、实时数据能力或完整智能化能力。

Demo 阶段明确不提前引入
高德、百度等第三方地图 SDK
城市级实时定位
城市级导航
GeoHash、空间索引等复杂地理基础设施
Redis、实时数据流
传感器数据
3DGS
完整 AR
复杂推荐算法

真实 POI 的 latitude / longitude 继续保留，为后续真实空间能力提供数据基础。

3. ExperienceRoute —— 主题体验路线

目标：验证平台区别于普通“店铺列表”的核心产品能力。

例如：

开发内容：

路线详情
用户查看路线中的 POI
核心边界

用户应该去哪里、为什么去。

因此：

ExperienceRoute

目标：让 Demo 具备真正的“决策入口”。

本阶段不使用大模型，不追求复杂推荐算法。

先实现 Rule-based Recommendation。

当前时间
活动
POI 类型
路线主题
营业状态

生成：

今日去哪
├── 推荐卡片 A
├── 推荐卡片 B
└── 推荐卡片 C

Recommendation Domain 负责：

推荐策略
推荐候选
推荐排序基础规则
推荐结果生成

Recommendation 只生成建议，不直接修改商户、活动、任务等业务状态。

跨域查询由 Application 层负责聚合，最终返回：

RecommendationCard

ActivityDetail

等 ReadModel。

A. 地图与导航能力增强

目标：从 Demo 空间展示逐步升级到真实城市空间能力。

A2. NavigationRoute

定义：

从当前位置 / POI A 到 POI B 的实际行走路径。

与 ExperienceRoute 严格区分。

ExperienceRoute
= 推荐去哪


NavigationRoute
= 实际怎么走

NavigationRoute 是导航能力产生的结果模型，不是 Street Domain 的核心业务实体，当前阶段不为此新增 Navigation Domain。

初期实现

可以使用：

街区节点
+
街区道路
+
Dijkstra / A*

实现街区内部基础导航。

后续产品化

当 Demo 已验证核心业务，并确实需要：

真实定位
城市级道路导航
真实步行路线
城市级 POI
实际地图数据

再接入：

高德
百度
腾讯
其他地图 Provider

第三方地图统一放在 Infrastructure / Provider。

技术实现必须遵循可替换原则：

TencentMapClient
AmapClient
BaiduMapClient

均不能进入 Domain。

不因为未来可能接入地图 SDK 而提前增加 MapService 等复杂抽象。

E2. Dynamic Spatial Overlay

将动态状态叠加在空间底座之上。

例如：

😌 空闲
🙂 正常
😤 排队
🔥 热门

Overlay 不属于 Street Domain 本身，而属于空间展示能力。

数据状态与视觉表现解耦：Overlay 表达的是数据状态（例如 CrowdStatus = BUSY），
前端自行决定视觉形式（例如显示 😤 正在排队），同一状态可按场景采用不同表现。

可以应用于：

2D地图
3DGS
全景
